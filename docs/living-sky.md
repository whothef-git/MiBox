# Approved living sky

The original geometric wallpaper, header, dock and launcher layouts remain in place. A clear-sky tint blends over the existing wallpaper at 15% opacity. The sun and moon are independently drawn at 50% opacity, with a brief horizon fade. Only the sun retains a soft halo; the moon has no exterior glow or ring. No new cloud or rain effects are added. The existing Weather-tab atmosphere is unchanged.

The approved textured update uses a 90px moon and 92px sun at 1920 × 1080, each 10px larger than its previous drawing area. The sun retains its decorative texture. The approved 2 November lunar update uses NASA's 4096 × 2048 LROC color mosaic and 1440 × 720 LOLA elevation data from the [CGI Moon Kit](https://svs.gsfc.nasa.gov/4720/), with credits and conversions recorded in [NOTICE](../NOTICE.md). `LunarSurface` projects the near-side surface onto a sphere, uses terrain normals for crater relief and applies Lommel–Seeliger reflectance. The calendar controls illumination and waxing/waning orientation. This is an ambient illustration, not a cast-shadow ray tracer or exact libration model.

The 4K source map is decoded with sampling during construction, then released. A cached 384 × 384 lunar disc is rebuilt only when illumination or phase orientation changes and displayed at the existing 90px diameter. This improves the source detail without claiming a 4K on-screen Moon at that size. Moon opacity remains 50%, the sky tint remains 15%, and the sun is unchanged. The older generated lunar asset is retained in source but is no longer referenced by this renderer.

The moon's current phase name appears below its disc in Outfit Regular at 14px, with an 8px gap to the top of the text at the reference resolution. This size was approved after comparing 10px/4px, 12px/6px and 14px/8px builds on the Sony TV. Muted blue-grey text at 70% opacity is centred on the full disc and follows its position and horizon fade. It is omitted with the moon when no recent lunar data is available, and is not shown under the sun.

The sun follows the existing local sunrise and Maghrib/sunset times. The moon follows a decorative night arc between sunset and sunrise; this is an ambient illustration, not a precise astronomical altitude/azimuth or moonrise prediction. The moon's illuminated fraction and waxing/waning side use the official USNO response for a specific UTC date and time, rather than the daily noon snapshot, a baked-in phase or a Hijri-day approximation.

`MoonCalendar` requests the documented `https://aa.usno.navy.mil/api/celnav` endpoint with the configured coordinates and the current UTC date/time, rounded down to a fifteen-minute interval. The [official API documentation](https://aa.usno.navy.mil/data/api) defines `moon_phase` and numeric `moon_illum` for that instant. The returned UTC date, time and timezone are checked before accepting it. Malaysia midnight correctly maps to the previous UTC date. This replaces the one-day endpoint whose fraction is calculated for local noon.

A successful response is cached privately with its timestamp and request URL. Refreshes run asynchronously every fifteen minutes while the launcher is visible; failures have a five-minute retry gap. The most recent snapshot remains usable during refresh or a brief outage, but is rejected after thirty minutes, after a location change or if the clock moves before its timestamp. Legacy daily cache values are not used. HTTPS certificate and hostname validation remain enabled. USNO only supplies these lunar fields when the Moon is visible at the requested coordinates; if no valid recent value is available, the moon is omitted until one loads. The sun and original wallpaper continue working offline. Values have the provider's percentage precision and refresh cadence; they are not a continuous live measurement.

Positions update every ten seconds while the launcher is visible, using normal time. Minute ticks handle date, illumination refresh and sunrise/sunset changes. Animation callbacks stop when paused, and the calendar executor shuts down with the activity. No continuous 30fps loop, new service, framework, or production timelapse is included.

`LivingSkyChecks` covers lunar parsing and invalid responses, UTC conversion, response timestamp validation, fifteen-minute request buckets, thirty-minute cache expiry, clock reversal, phase orientation, midnight arc math, translucent rendering, and a real time-specific official HTTPS calendar request on the TV. Build its test APK with `:app:assembleDebugAndroidTest -PtestRunner=tv.widgetv.home.LivingSkyChecks` and run `tv.widgetv.home.test/tv.widgetv.home.LivingSkyChecks`.

On 31 October 2026, all 31 targeted checks passed on the Sony TV. A temporary debug build showed the new textures over a 90-second accelerated day/night arc, captured on the TV and approved by the user. That preview accelerated celestial motion only; it did not change the system clock or test smart-device controls. The temporary timelapse hook was removed from the approved normal-speed implementation.

After replacing the daily noon snapshot, all 43 updated checks passed on the Sony TV, including the real time-specific USNO HTTPS request, which returned 74% illumination during the early-morning test on 31 October 2026. Cache and timezone edge cases use fixtures; the HTTPS response and rendering checks run on the TV. No smart-device commands were sent.

On 2 November 2026, all 54 updated checks passed on the Sony TV, including NASA asset loading, spherical rendering, transparent edges, phase orientation, surface detail, cache reuse, absence of an exterior halo, unchanged opacity and a real USNO response reporting 51% illumination. Debug and optimized release APKs built successfully. The optimized build was installed for visual review and approved. No smart-device commands, simulated date/time or weather overrides were used.
